## Решения, принятые на этапе, и их причины

**Метка берётся из имени файла, а не из папки.** Архив Zenodo оказался плоским:
999 файлов в корне, класс закодирован префиксом (`YellowRust1003.png`).
`resolve_class` сначала проверяет каталоги, потом префикс имени файла, поэтому
код переживёт и добавление данных с раскладкой «папка на класс».

**Дубликаты ищутся dHash, а не только md5.** Побайтовых копий в наборе нет
(0 совпадений по md5), но одна пара кадров оказалась визуально идентичной.
Один md5 такие случаи не ловит, поэтому нужен перцептивный хэш. Полный перебор
пар на 998 изображениях — около 500 тысяч сравнений 64-битных чисел, то есть
доли секунды; индексные структуры здесь излишни.

**Разбиение групповое, а не просто стратифицированное.** Датасет снят в поле,
и один лист мог попасть в несколько кадров. Если такие кадры разъедутся между
train и test, модель на тесте узнает уже виденную картинку и метрика этапа 5
будет завышена. Поэтому кадры с расстоянием dHash ≤ 12 внутри класса склеиваются
в «сцену» и уходят в одну выборку целиком. Порог 12 мягче порога удаления (4):
похожий кадр — это полезный обучающий пример, терять его не нужно, а вот
разделять со своей парой нельзя.

**Порог удаления 4, а не 0.** При 0 не находится ничего сверх md5, при 4
находится реальный дубликат, подтверждённый глазами. Более высокие пороги
начинают удалять разные снимки одной делянки, то есть уничтожать полезные данные.

**Контактные листы сохраняются в JPEG.** В PNG каждый лист весит около 1,7 МБ,
пять листов — 8,5 МБ в репозитории при каждой пересборке. JPEG q=88 даёт
350 КБ при том же качестве осмотра.

**Изображения не версионируются.** `data/raw/` в `.gitignore`: 1 ГБ в git
не нужен, а `src/data/download.py` со сверкой md5 восстанавливает набор точно.
В git попадают только CSV с путями и метками — они весят килобайты и полностью
описывают состав выборок.

## Что нашла визуальная проверка

Просмотр контактных листов дал пять замечаний, которые повлияют на качество
модели. Все они выписаны в раздел «Известные особенности»
[`docs/DATASET.md`](../DATASET.md); главное из них:

> Класс `mildew` снят в другой обстановке — горшки, теплица, бетонный пол, —
> тогда как остальные четыре класса сфотографированы в поле. Модель может
> выучить фон вместо симптома.

Это именно то, что этап 3 и должен был обнаружить до начала обучения: дальше,
на этапе 9, гипотезу нужно будет проверить на матрице ошибок.

## Артефакты этапа

```
configs/dataset.yaml                    источник, классы, пороги, доли выборок

src/data/hashing.py                     md5 и dHash
src/data/inventory.py                   проверка классов и целостности файлов
src/data/dedup.py                       поиск дубликатов, группировка сцен
src/data/split.py                       разбиение на train / val / test
src/data/preview.py                     контактные листы и HTML-отчёт
data/interim/inventory.csv              999 записей: класс, размер, md5, dHash
data/interim/duplicates.csv             удалённые дубликаты с обоснованием
data/interim/clean.csv                  998 записей с номером сцены
data/processed/splits/*.csv             train / val / test / all
reports/stage3/*.json                   сводки по шагам в машинном виде
reports/stage3/previews/*.jpg           контактные листы по классам
reports/stage3/dataset_review.html      страница визуальной проверки
docs/DATASET.md                         паспорт датасета
```

## Проверка результата

```bash
python -m src.data.download
python -m src.data.inventory
python -m src.data.dedup
python -m src.data.split
python -m src.data.preview
open reports/stage3/dataset_review.html
```

Ожидаемый вывод: 999 проиндексировано, 0 отбраковано, 1 дубликат удалён,
998 изображений, разбиение 700 / 149 / 149.
